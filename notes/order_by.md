# Обоснование ORDER BY в ClickHouse

## fact_sales
ORDER BY (date_id, store_id, product_id, sale_id)

Порядок отражает типичные разрезы запросов из паспорта:
- **date_id первым** — большинство запросов фильтруют по периоду
  («оборот за январь», «по месяцам»). Date первым → ClickHouse
  читает меньше кусков.
- **store_id вторым** — оборот по регионам/магазинам через JOIN
  с dim_store, фильтрация по магазину эффективнее при таком порядке.
- **product_id третьим** — топ категорий: JOIN с dim_product.
- **sale_id последним** — уникален в пределах дня, даёт стабильный
  порядок внутри одного date_id.

## dim_product
ORDER BY (product_id, valid_from)

SCD2: один товар → несколько версий. Сортировка по product_id,
затем по valid_from — так запросы «все версии товара X» читают
соседние строки, а фильтр по действующей версии (valid_from <= дата)
работает эффективно.

## dim_store
ORDER BY (region, city, store_id)

Основной разрез — регион. Сортировка по region → city даёт
эффективное чтение при запросах «оборот по регионам» и «по городам».

## dim_date
ORDER BY (year, month, date_id)

Основной разрез — год/месяц. Сортировка по year → month
ускоряет фильтры «за январь», «за 2024 год».

## Важно
`ORDER BY` в MergeTree — это **не уникальный ключ**, а порядок хранения
на диске. Дубли не запрещаются. Идемпотентность загрузки обеспечивается
через `TRUNCATE TABLE` перед загрузкой (см. `etl/load_ch.py`).
